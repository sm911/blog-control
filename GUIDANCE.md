## Voice & Authority

Security Medic content speaks in the voice of **Jim Venuto**, fractional CISO and founder. The tone is:

- **Practical, not theatrical.** Real security work for real organizations. No Hollywood "hacker in a hoodie" drama, no breathless "zero-day apocalypse" hyperbole.
- **Framework-first.** NIST CSF 2.0, HIPAA Security Rule, NYDFS 23 NYCRR 500, SOC 2, ISO 27001 — these are the blueprints. Security Medic builds programs on frameworks, not vendor FUD.
- **Vendor-neutral.** We evaluate and recommend tools, but Security Medic does not sell software or claim to operate a 24/7 SOC. We're advisors, not product resellers.
- **Regionally grounded.** Hudson Valley and New York focus. We understand NYDFS reporting deadlines, New York insurance market realities, and the constraints of mid-Hudson MSPs and Main Street practices.
- **No fake case studies.** Do not invent client names, metrics, breach scenarios, or testimonials. If a real example exists, use it with permission. Otherwise, speak in principles and patterns.

## Target Audiences

Security Medic serves five primary audiences, each with distinct pain points and buying triggers:

### 1. **SMB (Small & Medium Business)**
- **Pain:** Cyber insurance questionnaire they can't answer; compliance mandate from a larger customer; first-time audit requirement.
- **Triggers:** Insurance renewal, contract requirement, board/investor due diligence.
- **Language:** Plain English, avoid jargon, explain "why this matters" before "how to do it."
- **Proof:** Framework alignment, insurance approval stories, cost-effective roadmaps.

### 2. **Private Enterprise**
- **Pain:** Shadow AI sprawl, supply chain vendor risk, inadequate security staffing, compliance drift.
- **Triggers:** M&A due diligence failure, material weakness identified, executive turnover, new regulation.
- **Language:** Risk quantification, board-ready reporting, operational resilience.
- **Proof:** Policy templates, risk registers, executive briefing decks.

### 3. **Public Sector (SLED: State, Local, Education)**
- **Pain:** Budget constraints, civil service hiring limits, antiquated procurement rules, unfunded mandates.
- **Triggers:** State mandate (e.g., NYS cybersecurity requirements for local governments), grant opportunity, public breach in peer jurisdiction.
- **Language:** Compliance-first, cost justification, grant eligibility, peer benchmarking.
- **Proof:** Grant application support, policy samples vetted for public sector use, peer-district comparisons.

### 4. **K-12 & Secondary Education**
- **Pain:** Student data privacy (FERPA, COPPA), limited IT staff, Chromebook/Google Workspace sprawl, BYOD chaos.
- **Triggers:** State student privacy audit, ransomware incident at peer district, new EdTech vendor contract.
- **Language:** Student safety, FERPA compliance, superintendent/board accountability, "what other districts are doing."
- **Proof:** FERPA program templates, student data inventory worksheets, incident response plans for schools.

### 5. **MSPs (Managed Service Providers)**
- **Pain:** Clients asking compliance questions the MSP can't answer; insurance carriers demanding MSP security attestations; no one on staff with CISO experience.
- **Triggers:** Client audit failure, insurance requirement for MSP vCISO coverage, RFP demands for compliance expertise.
- **Language:** White-label support, client-facing deliverables, compliance program scaffolding they can brand and deploy.
- **Proof:** MSP partnership models, vCISO co-delivery frameworks, compliance-as-a-service packaging.

## Content Length & Structure

### Blog Posts
- **Target length:** 800–1,500 words unless the blog has established longer norms (e.g., leadership-blog series essays).
- **Structure:**
  - **Lead:** Problem, stakes, or news hook (1–2 paragraphs).
  - **Body:** Framework/principle explanation, real-world application, step-by-step guidance or analysis.
  - **Close:** Summary action, next step, or link to related resource.
- **Formatting:**
  - Use headers (H2, H3) to break up long sections.
  - Bullet lists for action steps, checklists, or multi-part requirements.
  - Bold key terms on first use.
  - Code blocks or tables for technical content (policies, NIST Functions, control mappings).

### One-Pagers & Presentation Material
- **One-pagers:** 1 page, dense. Problem, solution, proof. PDF or markdown with export-ready layout.
- **Talk tracks:** 2–3 pages. Conversational script for sales calls or client meetings. Anticipates objections, includes "what to say when they ask about cost."
- **Slide outlines:** 8–12 slide structure. Title, key visual/stat per slide, presenter notes. No final slides — these are outlines for custom decks.

## Post Metadata Requirements

Every blog post must include a metadata block as an HTML comment at the top of the file. This metadata powers the blog-control template system and ensures consistent indexing.

### Required Metadata Format

```html
<!-- blog-control-meta
title: Your Post Title Here
author: Jim Venuto
date: YYYY-MM-DD
category: Primary Category
tags: tag1, tag2, tag3
read_time: X min
description: One-sentence summary for meta tags and index listings (150–160 characters)
-->
```

### Optional Metadata

```html
series: Series Name (if part of a multi-post series)
priority: P1 | P2 | P3 (P1 = urgent/featured, P2 = standard, P3 = evergreen)
featured_pin: true (keeps post featured on index regardless of rotation logic)
canonical_url: https://other-site.com/original-post (if republished from another source)
```

### Metadata Field Definitions

- **title:** Post headline. Should be compelling, specific, and under 80 characters for meta tags.
- **author:** Default "Jim Venuto" unless guest post.
- **date:** Publication date in ISO format (YYYY-MM-DD). Used for sorting and recency scoring.
- **category:** One primary category from the blog's category list (see blog theme files in `themes/`).
- **tags:** Comma-separated list of specific topics, technologies, or frameworks mentioned. Used for filtering and related post suggestions.
- **read_time:** Estimated reading time in minutes. Blog-control can auto-calculate this from word count, but manual entry allows for adjustment based on complexity.
- **description:** Meta description for SEO and social sharing. Should be a one-sentence summary, 150–160 characters. This appears in search results and Open Graph previews.
- **series:** If the post is part of a named series (e.g., "LiteLLM Supply Chain Attack Series"), list the series name. Blog-control uses this to link related posts and boost featured rotation scoring for active series.
- **priority:** P1 posts are urgent/newsworthy and should be featured prominently. P2 posts are standard content. P3 posts are evergreen reference material. Featured rotation logic weighs P1 posts higher.
- **featured_pin:** Set to `true` to manually pin a post in the featured section indefinitely. Use sparingly for flagship content or active campaigns.
- **canonical_url:** If this post was originally published elsewhere (e.g., LinkedIn, Medium, partner blog), include the canonical URL to avoid SEO duplication penalties.

### Missing Metadata

If blog-control encounters a post without the required metadata block, it will:
1. Log a warning in the audit output.
2. Attempt to extract title and date from the filename or first H1 heading.
3. Default to "Uncategorized" and today's date if extraction fails.

**Fix missing metadata immediately.** Audit your blog with `./blog-control.sh audit --blog <blog-name>` to identify posts that need metadata blocks added.

## Publishing Workflow

### Default: PR + Draft Review
- **All new posts and blog changes default to pull request + draft status.** Do not push directly to `main` or publish live without review.
- The Blog Content Agent opens a PR for every new post or template change.
- Jim (or designated reviewer) reviews the PR before merging.
- **Exception:** Urgent news posts (e.g., active supply chain incident, breaking regulatory change) may be published directly if Jim has pre-approved the topic and urgency is documented.

### Live Publishing (Explicit User Command Only)
- Only publish directly to main and live if the user explicitly says "publish live" or "push to production."
- Before live publish, confirm:
  - Metadata is complete and accurate.
  - Links are tested and functional.
  - CTA points to the correct service site.
  - Post follows GUIDANCE voice and structure rules.

### Marketing Site Code Changes
- **Never push code changes to securitymedic.com, hudsonvalleyciso.com, cyberintelpro.com, or privacymedic.com without consulting the Marketing Wizard agent first.**
- Blog content changes (adding a post to a blog repo) do not require Marketing Wizard review.
- Changes to site templates, navigation, service pages, or pricing require Marketing Wizard approval and staging review before production deployment.

## Avoiding Common Pitfalls

### Do NOT:
- Invent client names, breach scenarios, or metrics. If you don't have real data, speak in patterns and principles.
- Use vendor product names as the solution. Security Medic recommends tools but does not sell them. Focus on the control or capability, not the brand.
- Claim Security Medic operates a 24/7 SOC, sells software, or provides services outside our actual offerings (fractional CISO, compliance programs, assessments, AI governance).
- Overuse security jargon. If the audience is SMB or public sector, explain terms on first use.
- Write "thought leadership" fluff with no actionable guidance. Every post should teach the reader something concrete or help them make a decision.
- Publish without metadata. The blog-control system depends on accurate metadata for indexing, rotation, and SEO.

### DO:
- Link to primary sources: NIST publications, regulatory text, framework standards, vendor security advisories.
- Provide templates, checklists, or step-by-step runbooks when the topic calls for it.
- Acknowledge complexity and trade-offs. Security is not binary. "Here's the ideal approach, and here's the pragmatic version for orgs with limited budget."
- Use real examples with permission, or anonymize carefully ("a mid-sized medical practice we worked with" is fine; inventing "Dr. Smith's Clinic" is not).
- Cross-reference other Security Medic blog posts when relevant. Build a web of related content.

## Editorial Standards

### Accuracy
- Cite sources for statistics, compliance requirements, and technical claims.
- If a regulation or standard has been updated, confirm you're referencing the current version.
- If a tool or technique is deprecated, note that and suggest the modern alternative.

### Clarity
- Write for the audience's expertise level. SMB posts should avoid assuming deep technical knowledge. Practitioner posts (cloud-architecture, data-security) can assume familiarity with core concepts.
- Define acronyms on first use in each post, even if they're common in the field.
- Use active voice and concrete examples.

### Consistency
- Follow the blog-control metadata format for all posts.
- Use the blog's designated category list (see theme files in `themes/`).
- Link to Security Medic service sites using full URLs, not relative paths (blog posts live on GitHub Pages, service sites may live elsewhere).
